System Deep Dive

Bitamin Platform Architecture

Real-time messaging and workflow automation platform. Designed to handle concurrent, multi-channel event streams with full workflow orchestration.

WhatsApp / Instagram → Ingestion Service → NATS Pub/Sub → Worker Pool → Workflow Engine
Workflow Engine → Integration Adapters → Zoho / Razorpay / IndiaMART
All Services ↔ PostgreSQL + Redis (cache + ephemeral state)
Each tenant runs with isolated workflow configuration and data boundaries.
Migration

Node.js → Golang

Node.js handled early product velocity well, but goroutines gave us true concurrency for high-throughput workloads — particularly processing thousands of simultaneous webhook events without the event loop becoming a bottleneck. The switch also eliminated an entire class of callback-complexity bugs.

Migration

RabbitMQ → NATS

RabbitMQ's exchange/binding model added operational surface area with limited upside for our use case. NATS gave us lower latency, a simpler topology, and drastically reduced operational overhead — no broker management, no complex routing configuration to maintain.

Design

Integration Adapter Pattern

Wrote the first three integrations directly against core messaging logic — a mistake I corrected quickly. Built a typed adapter interface so all third-party connectors are isolated behind a contract. New integrations now ship without modifying the workflow engine at all, and failures in one adapter cannot cascade.

Design

gRPC for Internal Services

REST over HTTP/1.1 was adding latency on the hot path between internal services. gRPC with protobuf contracts gave us typed interfaces, lower serialization overhead, and bi-directional streaming support for real-time analytics pipelines currently in development.

Engineering Philosophy

How I think about systems

Complexity belongs in infrastructure, not application code.

A well-designed event bus, adapter interface, or job queue absorbs complexity so that the services consuming them stay simple and focused. I design systems where the hard parts are clearly located.

Migrations are a product problem, not just a technical one.

Stack decisions have business consequences. I've led migrations by making the case — clearly — for what changes, what risk is involved, and what the team gets in return. Then executing incrementally.

The most important interface is the one between services.

Internal contracts (gRPC, event schemas, adapter interfaces) deserve more rigor than public APIs. They're harder to change and failures are less visible. I treat them as first-class design artifacts.

Scale the team's thinking, not just the system.

A staff engineer's highest leverage is making other engineers think more clearly about trade-offs, failure modes, and long-term cost. Documentation, design reviews, and code review culture matter.

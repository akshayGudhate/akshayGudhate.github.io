Case study/Platform Migration

Moving Bitamin to Go, NATS and DBOS

Leading the full re-architecture of Bitamin, a live messaging platform, from Node.js + RabbitMQ to Go, PostgreSQL, DBOS, NATS and Cloudflare R2 — for better concurrency, crash-safe workflows, a smaller operational surface, and typed contracts between services.

Key decisions

Why migrate at all

I knew this stack's limits first-hand: I built Bitamin on Node.js + RabbitMQ at Biz Secure Labs and ran it in production from 2021 to 2025. These decisions come from operating it, not from reading about it.

Migration

Node.js → Golang

Node.js handled early product velocity well, but goroutines gave us true concurrency for high-throughput workloads — particularly processing thousands of simultaneous webhook events without the event loop becoming a bottleneck. The switch also eliminated an entire class of callback-complexity bugs.

Migration

RabbitMQ → NATS

RabbitMQ's exchange/binding model added operational surface area with limited upside for our use case. NATS gave us lower latency, a simpler topology, and drastically reduced operational overhead — no broker management, no complex routing configuration to maintain.

Migration

Async jobs → DBOS durable workflows

Long-running work like multi-step workflows and third-party calls now runs as DBOS workflows. Each step is checkpointed in PostgreSQL, so a crash or deploy resumes the workflow exactly where it stopped instead of re-running or losing it — and there is no separate orchestrator cluster to operate, because the state lives in the database we already run.

Service contracts

Typed interfaces between services

Design

gRPC for Internal Services

REST over HTTP/1.1 was adding latency on the hot path between internal services. gRPC with protobuf contracts gave us typed interfaces, lower serialization overhead, and bi-directional streaming support for real-time analytics pipelines currently in development.

Where it is now

What I'm driving next

  • High availability — a distributed consumer-group topology and graceful failover under load for the next availability tier.
  • gRPC contracts across the platform — typed, low-latency internal communication that also opens the door to real-time analytics.
  • Engineering standards — code review process, service design principles, and on-call runbooks for production readiness.
How I run migrations

Migrations are a product problem, not just a technical one. I make the case clearly — what changes, what the risk is, what the team gets in return — and then execute incrementally instead of in one big switch.

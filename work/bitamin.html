The problem

Many channels, many tenants, one platform

Messages arrive from several channels at once, as webhooks, often in bursts. Every tenant has its own workflows and its own third-party tools. The platform has to accept every event, run the right workflow, and talk to CRMs and payment providers — without one busy tenant or one broken external API slowing everyone else down.

Architecture

How an event moved through the original system

Ingestion is separated from processing by RabbitMQ, so bursts queue up instead of piling onto the workflow engine.

WhatsApp / Instagram → Ingestion Service → RabbitMQ → Worker Pool → Workflow Engine
Workflow Engine → Integration Adapters → Zoho / Razorpay / IndiaMART
All Services ↔ PostgreSQL + Redis (cache + ephemeral state)
Each tenant runs with isolated workflow configuration and data boundaries.
This is the original Node.js + RabbitMQ design. The Go + NATS + DBOS version is covered in the migration case study.
The insight that changed my approach

Integrations belong behind a contract

Design

Integration Adapter Pattern

Wrote the first three integrations directly against core messaging logic — a mistake I corrected quickly. Built a typed adapter interface so all third-party connectors are isolated behind a contract. New integrations now ship without modifying the workflow engine at all, and failures in one adapter cannot cascade.

When things go wrong

Designing for failure, not just the happy path

  • Async jobs with retry semantics — work that fails is retried by the job system, not lost or retried by hand.
  • Failure isolation between integrations — a slow or failing third-party API stays inside its own adapter and cannot cascade into messaging.
  • Tenant boundaries — each tenant runs with isolated workflow configuration and data boundaries.
  • Hot-path database work — query profiling, composite indexes and materialized views where reads were heaviest.
What this project taught me

Complexity should live in the infrastructure, not the application layer. A good event bus, adapter interface or job queue absorbs the hard parts, so the services built on top stay simple. And the cheapest time to put a contract in place is before the third integration, not after.
